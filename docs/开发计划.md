> - 可以输入帧号定位。
>

**验收范围（1.5.0）**：`npm test` 全部通过（数量见 CHANGELOG 发布时的记录）；`node mmd-plugin/tests/e2e.mjs`、`node tests/desktop.mjs`、`node tests/desktop-recovery.mjs` 通过。没有做：长时间真实素材的剪辑验收、真实 MMD 场景里的智能剪切、打包版冷启动测速。下文各步的测试数量是当时的快照。

### 复审后的现状（2026-10-22）

- **索引**：ffprobe 的包列表逐行流式读取（`-of compact`），只保留每包的时间戳和关键帧的位置 / 大小；只读关键帧包的 NAL 类型；安全切点检查为 O(N)。可以取消：移除片段、清空、关闭软件时停止读取。实测 24,000 帧全 IDR 的小文件索引在 5 秒内（测试里的上限），不代表任意长片的耗时。
- **还没做**：跨重启、带版本的索引缓存；索引进度显示；把索引移到 worker。
- **MKV 等容器的 H.264 / HEVC**：本次运行内只复制一次到临时 MP4，索引和导出共用；最后一个用到它的片段移除、清空或关闭软件时删除。
- **可变帧率（VFR）**：一期直接拒绝并提示先转成固定帧率；时间码模式留到以后。
- **时间轴不从 0 开始的文件**：seek 时间按容器的 start_time 换算；导出后核对总帧数，不对就删除结果并报错。
- **生命周期**：没有提炼共用的调度模块。改为互斥：剪辑导出时不能开始压制 / 音视频处理、检测编码器、管理工具、应用更新；退出确认和退出等待都把剪辑导出算作运行中；关闭软件会中止导出、预览和索引并清掉临时文件。
- **取消**：导出可以取消（每个 FFmpeg 进程都收中止信号，删除半成品）；索引在移除 / 清空 / 关闭时取消。界面上没有单独的“取消读取”按钮。
- **预览**：最近看过的帧（总量 32 MB 以内）直接复用，不再启动 FFmpeg。

1.4.3 的 Hi-Res 做法见 README“音视频提取与合并”和 CHANGELOG：用一个纯函数决定直接复制、无损转码还是重采样，并给出原因。

一期的顺序是**先证明底层正确，再接界面**。审查时的定向实验已经说明：只靠 `packet.flags` 和 concat 的 `inpoint/outpoint`，保证不了承诺的帧边界。

## 一、一期第 1 步：独立的裁切 / 拼接验证程序

先写一个命令行程序（不进界面）。输入“文件 + 显示范围”，输出拼接结果，并附逐帧验证报告。接界面之前，这一步必须在全部验收素材上通过。

### 结果（2026-10-22，已完成）

- 代码：`backend/trim.cjs`（索引、吸附、片段检查、兼容检查、裁切拼接、音频）和 `scripts/trim-check.cjs`（验证程序）。
  - 用法：`node scripts/trim-check.cjs --out 输出 文件:起-止 …`
  - `--matrix` 生成各格式样本，并输出下表。
- 测试：`tests/trim.test.cjs`。当时全部 77 个测试通过。
- **裁切方法**：每段先 seek 到起点 IDR 的时间再往后半帧（demuxer 会落在这个 IDR 上），用 `-frames:v` 按包数精确复制；最后用 concat demuxer 拼接各段，不设 inpoint / outpoint，并加 `-auto_convert 0`。
  - 原计划的 concat `inpoint/outpoint` 在有 B 帧时每段少 3–4 帧，已放弃。
  - concat 默认的 `auto_convert` 会给 H.264 每段第一个包加上 SPS/PPS（多 38 字节），关掉后逐包一致。
  - MKV 里的 H.264 / HEVC，FFmpeg 的 seek 不可靠，会从头开始。这类文件先把视频包原样复制进临时 MP4，再从临时 MP4 切；同样无损。
- **安全切点**：
  - H.264 读关键帧包的 NAL 类型，只认 IDR（5）；HEVC 只认 IDR（19 / 20）。
  - 另外检查：这个 IDR 之后解码的帧都不早于它显示，之前解码的帧也都不晚于它显示。
  - 全帧内编码按容器的关键帧标记判断。FFV1 默认并非每帧独立，只有关键帧能切。
- **验证**：每次结果都核对三项：
  1. 解码后逐帧 MD5 与源对应帧相同；
  2. 视频包逐包相同；
  3. 解码时间递增（MKV 不记录解码时间，跳过这一项）。

  使用 PCM 时，音频按采样点与源逐个比较，包括接缝处。实测 AAC 源最大差值为 0；源音频不够长时补的是静音，总长度与视频一致。

- **索引速度**：4K 60 fps、402 帧的 H.264 约 0.1 秒，600 MB 的 ProRes 约 0.2 秒；只读取关键帧包的内容。

| 格式                                  | 可切位置   | 结果                                   |
| ------------------------------------- | ---------- | -------------------------------------- |
| H.264 x264（有 / 无 B 帧，MP4 / MKV） | 每个 IDR   | 通过，逐帧、逐包一致                   |
| H.264 NVENC                           | 每个 IDR   | 通过                                   |
| H.264 x264 开放 GOP                   | 只有开头   | 拒绝：关键帧不是 IDR，从这里开始会花屏 |
| HEVC NVENC                            | 每个 IDR   | 通过                                   |
| HEVC x265 默认（开放 GOP，CRA）       | 只有开头   | 拒绝                                   |
| HEVC x265 闭合 GOP                    | 每个 IDR   | 通过                                   |
| ProRes 422 HQ / 4444（带 Alpha）      | 逐帧       | 通过，Alpha 保留                       |
| UtVideo                               | 逐帧       | 通过                                   |
| FFV1                                  | 每个关键帧 | 通过                                   |
| VP9、AV1 等其他编码                   | —          | 拒绝（暂不支持）                       |

**发现**：MMDEncoder 自己的 NVENC 预设没有指定 GOP，实测约每 250 帧才一个 IDR（60 fps 下约 4 秒），H.264 成片的切点很稀；软件编码的 x265 默认开放 GOP，导出的 HEVC 只能从开头切。要不要给预设加“剪辑友好（短 GOP、闭合 GOP）”选项，需要用户决定。代价是同画质下文件变大，实测如下：素材为测试1（4K 竖屏、60 fps、402 帧，画面约八成透明），用内置“默认 4K”预设，恒定质量下画质不变，只有大小变化。

| 关键帧间隔        | 默认 4K · 硬件（NVENC CQ 29） | 默认 4K · 软件（x264 CRF 21） | 6.7 秒内可切位置 |
| ----------------- | ----------------------------- | ----------------------------- | ---------------- |
| 默认（约 250 帧） | 23.5 MiB                      | 18.2 MiB                      | 2                |
| 120 帧（2 秒）    | 23.7 MiB（+1%）               | 18.6 MiB（+2%）               | 4                |
| 60 帧（1 秒）     | 24.0 MiB（+2%）               | 19.2 MiB（+5%）               | 7                |
| 30 帧（0.5 秒）   | 24.7 MiB（+5%）               | 20.5 MiB（+13%）              | 14               |

在这份 402 帧样本和上述设置下，编码速度没有明显变化；其他素材、其他编码器未测。画面复杂、运动多的素材，体积增幅可能更大。

软件编码的 HEVC（x265，CRF 21，同一素材）开放 / 闭合 GOP 的对比：

| 设置                             | 大小               | 6.7 秒内可切位置 | 与原片 SSIM | 编码时间 |
| -------------------------------- | ------------------ | ---------------- | ----------- | -------- |
| 开放 GOP（x265 默认，约 250 帧） | 15.63 MiB          | 1（只有开头）    | 0.99262     | 16.2 秒  |
| 闭合 GOP（约 250 帧）            | 15.64 MiB（+0.1%） | 2                | 0.99262     | 16.1 秒  |
| 开放 GOP · 1 秒                  | 15.97 MiB（+2.2%） | 1                | 0.99274     | 16.6 秒  |
| 闭合 GOP · 1 秒                  | 16.04 MiB（+2.6%） | 7                | 0.99271     | 15.7 秒  |

闭合 GOP 本身几乎不增加体积（+0.1%~0.4%），画质和速度不变；体积主要由关键帧间隔决定。

**还没做的**：

- 直接复制原音频（按包边界报告误差）；
- HEVC Alpha（NVEncC）的辅助层检查。

取消裁切已在第 2 步做了，见下文。

### 1. 两套索引分开保存（P02、P07）

- **包索引**：每个视频包记录流索引、整数 PTS / DTS、time_base、duration、关键帧标记。
  - 用 ffprobe `-show_packets` 流式读取，不经过 `service.run()`：`run()` 只保留最后 1 MiB 输出，长索引的前半段会丢。
  - 读取可以取消，并显示进度。
- **显示帧索引**：按显示顺序给每一帧编零基帧号，记录它的 PTS，以及解码它需要从哪个包开始。
  - B 帧会让解码顺序和显示顺序不同。不能简单把包 PTS 排序当成所有格式通用的帧索引。
- **安全切点类型**：按编码分别判断，不用统一的“IDR”标签。
  - H.264 / HEVC 用码流解析（`trace_headers` 或解析 NAL）区分 IDR、CRA / BLA 和普通关键帧。审查实验里，开放 GOP 的 x264 在 0、1、2、3 秒都有 `K` 包，却只有一个 IDR。
  - ProRes、UtVideo 每帧都可以作切点；FFV1 默认并非每帧独立，只有关键帧可以（见第 1 步结果表）。
  - 无法证实是安全切点的帧，**拒绝作为切点并说明原因**，不把普通关键帧自动当成 IDR。
- **缓存**：存后端，带 schema / 探测器版本；源文件的大小或修改时间变了就重建。规定缓存容量与清理方式；原文件找不到时明确标为“源文件丢失”。界面按需只取一段时间范围的索引，不一次拿全片。
- **缺失时间戳、非零起始 PTS、编辑列表**：显式降级处理，并在报告里写明。

### 2. 帧号与吸附规则（P02）

- 帧号从 0 开始。片段为 [入点, 出点)，出点那一帧不包含在内。
- **出点可以是“文件末尾”**。否则全帧内素材的最后一帧、或只有开头一个 IDR 的文件的尾段都选不进来。
- 吸附：入点和出点都吸附到最近的安全切点。前后一样近时取前一个。超出范围时夹到文件首尾。入出点吸附后重合时，提示“这一段吸附后为空”，不导出。
- MMD 帧号换算用有理数帧率，例如 `round(MMD 帧号 × 60000/1001 ÷ 30)`，避免长时间轴上累积误差。
- 可变帧率（VFR）素材：原计划只提供时间码模式；一期实际做法是直接拒绝。

### 3. 从显示范围到能解码的包范围（P01）

- concat demuxer 的 `outpoint` 按 **DTS** 判断，界面上的 **PTS** 不能原样当作裁切边界。审查实验：带 B 帧的闭合 GOP H.264 拼接 [0,1) 和 [2,3) 两段，预期 60 帧，实际解码得到 64 帧。
- 验证程序要建立明确的映射：用户选的显示范围 → 必须包含的包范围（从安全切点的包开始，到出点前最后一个显示帧所依赖的包为止）→ 输出时间戳。
- 候选做法：
  1. 按包范围逐段 `-c copy` 写临时片段，再无损拼接；
  2. 用 bitstream filter 或自写的包级裁切；
  3. concat 列表加上修正后的 inpoint / outpoint。

  三种都在全部素材上跑。只采用**按帧内容验收**通过的做法，不能只比较容器总时长。`-avoid_negative_ts make_zero` 只处理时间戳偏移，不能证明裁切正确。

### 4. 拼接兼容检查（P03）

- 各段必须一致：编码、档次 / 级别、分辨率、像素格式、SAR、帧率、time_base、场序、色彩（range / matrix / primaries / transfer）、旋转元数据，以及 Alpha 附加信息（如 HEVC Alpha 的辅助层）。
- **比较实际参数集**（extradata / SPS / PPS / VPS），不看编码器名称。“同一编码器”不保证参数集兼容，“不同编码器”也不一定不兼容。
- 一期对未经验证的参数集变化**直接阻止导出**，并说明是哪一段、哪个参数。以后针对验证过的情况再放宽。

### 5. 音频（P04）

视频无损复制，音频单独生成，最后合并。

- **默认：重新编码原音频**。
  - 每段按吸附后的实际时间范围 `atrim`，再 `asetpts=PTS-STARTPTS` 重置时间戳；
  - 统一采样率和声道布局后用 `concat` 接起来。
- **接缝**：不做任何淡入淡出（2026-10-22 用户决定），各段音频按采样点首尾直接相接。也不用 `acrossfade`：它会让相邻两段重叠，审查实测两段各 1 秒，接起来只有 1.995 秒，多段累计后会偏移。
- **补齐**：某段没有音轨、音轨比画面短、外部音频不够长时，补静音，总长度始终以视频为准。不使用 `-shortest`（1.4.3 修的 MMD 截短问题就是它造成的）。
- **直接复制原音频**：只在各段音频参数一致时可选。导出前按实际包边界算出接缝误差、首尾延迟和累计偏移，超过一帧时提示改用重新编码。不写“AAC 约 21 毫秒”这种通用常量：AAC 一帧固定 1024 个采样点，实际时长随采样率而变。
- **替换为外部音频**：可设起点偏移，并写明正负的含义：正数表示音频从自身的第 N 秒开始用，负数表示视频开头先空 N 秒再接音频。可以用 MMD 帧号对齐。不做淡入淡出。
- **无音频**。

### 6. 无损验收（P06）

验收分两层：

1. **码流层**：导出流程中没有视频编码器和视频滤镜。在相同码流表示下比较压缩载荷（必要的重封装变化，例如 H.264 在 MP4 长度前缀和 Annex B 之间的转换，要先统一再比较，并在报告里说明）。
2. **画面层**：用同一解码器、同一像素格式，分别解码源选段和输出，逐帧比较画面、顺序和帧数。另外检查 DTS 单调、片段边界、音画同步。不要求重置后的 PTS / DTS 与源完全相同。

HEVC Alpha 单独确认辅助层 / 相关 SEI 是否保留。主画面一致不等于透明信息完整。

### 7. 验收素材

- 不同 B 帧配置的 H.264：x264 默认、`bf=0`、NVENC；
- 开放 GOP 的 H.264；
- HEVC（NVENC）；
- ProRes 422 / 4444；
- UtVideo、FFV1；
- 声明支持的 Alpha 路径（ProRes 4444；HEVC Alpha 若支持）。

每种素材都要覆盖：首尾边界、只有开头一个 IDR、参数集变化被拒绝、短音频补静音、取消、输出重名。最后给出**格式支持矩阵**：每种格式标明“支持 / 仅逐帧 / 拒绝”及原因，写进 README。

## 二、一期第 2 步：接入界面（1.4.4）

### 结果（2026-10-22，已完成）

- 页面：`src/TrimTools.tsx`，第三个工作区“无损剪辑”。服务动作：`trimAdd` / `trimRemove` / `trimDuplicate` / `trimReorder` / `trimSet` / `trimFrame` / `trimExport` / `trimCancel` / `trimClear`。索引留在后端，界面只拿帧数、帧率和可切位置。
- 预览：每次只跑一个取帧进程，新请求会中止旧请求，界面丢弃过期结果。实测 H.264（MP4 / MKV）、HEVC、ProRes 的预览都是请求的那一帧（与相邻帧比较 PSNR）。
- 取消：裁切、拼接和音频的每个 FFmpeg 进程都接收中止信号；取消后删除半成品与临时文件夹。
- 测试：`tests/trim-service.test.cjs` 覆盖添加、吸附、预览、同文件多段、导出、不覆盖、拒绝不兼容文件、取消。当时全部 79 个测试通过；复审后又加了忙碌互斥、关闭时中止、移除时停止读取和清理临时文件的测试。
- 还没做：直接复制原音频；剪辑列表跨重启保存（一期只在本次运行期间保留）。

验证程序通过后再做。

- **新的工作区“无损剪辑”**：
  - 左侧是片段列表：添加文件、拖动排序，同一文件可以加多段；
  - 右侧是当前片段：预览、入点 / 出点、帧号输入，同时显示 MMD 帧号、视频帧号、吸附后的实际帧号三个值；
  - 底部是音频设置和导出。
- **键盘**：←/→ 逐帧；Shift+←/→ 跳到上一个 / 下一个安全切点；I / O 设入点 / 出点。时间轴滑条上标出安全切点的位置。
- **预览（P07）**：
  - 用 FFmpeg 取单帧，缩到 360p 的 JPEG；
  - 进程数有上限，最新的请求优先，过期的结果直接丢弃，拖动时不会堆积 FFmpeg；
  - JPEG 只显示主画面，不显示透明通道，界面写明“预览不显示透明”。
- **安全**：本地文件只通过主进程的自定义协议读取，只允许已加入剪辑页的文件，不放宽 `webSecurity`。
- **保存（P07）**：一期剪辑列表**只在本次运行期间保留**，关闭软件即清空。二期再做“保存剪辑工程（JSON）”，重开时要处理源文件丢失或已被修改的情况。
- **代码结构**：
  - `backend/trim.cjs` 放纯逻辑：索引解析、吸附、换算、兼容检查、音频滤镜图；
  - 原计划把任务调度、子进程运行和输出提交从 `service.cjs` 里提炼成共用小模块（审查报告第 4 节）。**没有落实**，改为忙碌状态互斥，见开头“复审后的现状”；
  - 界面在 `src/TrimTools.tsx`；
  - 新增 IPC 动作同时登记到 `desktop/main.cjs` 与 `desktop/preload.cjs`。

## 风险与对策

| 风险                                 | 对策                                                 |
| ------------------------------------ | ---------------------------------------------------- |
| 开放 GOP / 非 IDR 切点花屏           | 按编码解析随机访问类型；证实不了就拒绝作为切点       |
| B 帧让 DTS 和 PTS 不同，多出或少帧   | 显示范围 → 包范围的显式映射；逐帧画面验收            |
| 参数集不同的片段拼接后部分播放器出错 | 比较实际参数集，一期直接阻止                         |
| 音频接缝改变时长                     | 不做淡入淡出、不重叠；以视频长度为准，补静音         |
| 超长素材索引被截断 / 耗时            | 流式读取、可取消（已做）；进度和带版本的缓存（未做） |
| 预览请求堆积                         | 限制进程数，最新请求优先，丢弃过期结果               |
| VFR 素材帧号不准                     | 一期直接拒绝                                         |
